# AmberTrail

개발 중 저장된 파일을 자동 기록하고, 검토한 시점으로 복원하거나 선택한 스냅샷까지의 작업 구간을 순서대로 Git 커밋으로 확정하는 VS Code 확장 프로그램입니다.

기존 설치의 기록과 설정을 유지하도록 내부 확장 ID `dev-snapshot.dev-snapshot`과 명령·설정 접두사 `devSnapshot.*`는 유지합니다.

**Python이 저장·복원·Git 작업을 담당하고, TypeScript는 VS Code UI와 표준 입출력 통신만 담당합니다.** 외부 AI API, HTTP 서버, Python 서드파티 패키지를 사용하지 않습니다.

## 실행 조건

- 로컬 Windows, macOS, Linux의 VS Code Desktop 1.95 이상
- Git 2.43 이상과 활성화된 내장 Git 확장
- Python 3.12 이상 (별도 가상환경 실행 파일 사용 가능)
- 신뢰한 로컬 작업 폴더. 원격 SSH·WSL·컨테이너·웹·가상 워크스페이스는 MVP에서 제외합니다.

Python 인터프리터는 확장에 포함되어 있지 않습니다. 설치한 사용자는 Python을 준비하고, 필요하면 **사용자 설정**에서 다음 값을 지정하세요. 작업 프로젝트의 Python 선택 상태를 자동으로 사용하지 않습니다.

```json
{
  "devSnapshot.pythonPath": "C:\\path\\to\\log_venv\\Scripts\\python.exe"
}
```

macOS/Linux에서는 `/path/to/venv/bin/python`을 지정합니다. 빈 값이면 Windows에서 `python`, macOS/Linux에서 `python3`를 실행합니다. 변경 후 창을 다시 로드하세요. 코어는 `-I -S` 격리 모드로 시작하여 프로젝트 모듈, `PYTHONPATH`, site 패키지를 불러오지 않습니다.

## 개발 시작

이 저장소의 `log_venv`는 그대로 유지하고 Git에서 제외합니다. 확장 개발 모드와 개발 스크립트는 이 환경이 있으면 우선 사용합니다. 핵심 로직에 필요한 Python 패키지는 없습니다.

```powershell
npm ci
npm run check
npm test
npm run build
```

VS Code에서 저장소를 열고 F5의 **Run AmberTrail**을 실행한 뒤, Extension Development Host에서 기록할 Git 저장소를 여세요. 사이드바의 AmberTrail 아이콘에서 이력을 확인할 수 있습니다.

다른 Python으로 테스트하려면 `DEV_SNAPSHOT_PYTHON` 환경 변수에 실행 파일을 지정하세요. Python 테스트만 실행하려면 다음 명령을 사용합니다.

```powershell
.\log_venv\Scripts\python.exe -I -S -u backend\test_runner.py
```

`npm run test:integration`은 별도 사용자 데이터·확장 디렉터리에서 VS Code를 실행합니다. 기본적으로 테스트용 VS Code를 다운로드하며, `VSCODE_EXECUTABLE_PATH`를 지정하면 기존 실행 파일을 사용합니다. `VSCODE_VERSION=1.95.0`으로 지원 하한을 검사할 수 있습니다. 기존 VS Code 설정은 수정하지 않습니다.

`npm run package`는 로컬 `ambertrail-0.2.5.vsix`를 생성합니다. Marketplace에 게시하지 않습니다. Python 코어 소스는 VSIX에 포함되고 가상환경·테스트 데이터는 포함되지 않습니다.

## 사용 흐름

1. 저장소를 열 때 관리 범위에 기존 수정·미추적 파일이 있으면 기록된 HEAD와 비교한 변경 내용으로 작업 이름을 표시합니다. 변경이 없는 시작 상태는 타임라인에 올리지 않고 내부 비교 기준으로만 유지합니다. 내부 기준은 일반 기록 개수 한도에서 제외하며, 첫 변경의 Diff·복원을 위해 원본 바이트를 보존합니다. 동일한 파일 내용은 기존 객체를 재사용합니다. 이전 버전의 깨끗한 시작 기록도 숨기지만, 이름 지정·고정·커밋 연결한 기록은 계속 표시합니다.
2. 저장된 파일 변경 후 5초간 유휴 상태이거나 변경 시작 후 60초가 지나면 자동 캡처를 시도합니다. 캡처는 백그라운드 작업으로 실행하고 진행 상태를 표시합니다. 수동 캡처의 취소 버튼이나 자동 기록 일시 중지로 게시 전 캡처를 취소할 수 있습니다.
   **관리** 버튼 또는 명령 팔레트의 **AmberTrail: 기록 주기 설정**을 실행하면 사이드바 안에 관리 팝업이 열립니다. 세 값을 한 화면에서 입력하고 **주기 저장**을 누르세요. 변경 후 대기는 5초 단위, 연속 편집 중 최대 대기는 1분 단위, 전체 파일 내용 확인은 5분 단위로 변경할 수 있으며 기본값은 각각 **5초·1분·10분**입니다. 같은 팝업에서 저장 용량 확인, 기록 일시 중지·재개, 보존 정책 정리와 삭제 대상 선택도 제공합니다. Escape 또는 닫기로 팝업을 닫으면 입력 중인 주기는 저장하지 않으며, 삭제는 기존 보호 정책과 최종 확인 절차를 거칩니다. 설정은 작업 폴더에 저장하고 재로드 없이 적용하며 실행 중인 캡처가 있다면 먼저 취소합니다. 변경 내용이 같으면 새 스냅샷을 중복 생성하지 않습니다. 전체 파일 내용 확인은 관리 대상 파일의 해시를 다시 계산하며 테스트 실행이나 저장된 전체 이력의 무결성 검사는 아닙니다. VS Code 설정에서는 `devSnapshot.idleSeconds`, `devSnapshot.maxIntervalSeconds`, `devSnapshot.fullHashSeconds`를 초 단위로 직접 변경할 수 있습니다.
3. 타임라인은 날짜별로 기록을 모아 작업명·시각·브랜치·변경 파일 수를 표시합니다. VS Code의 밝은·어두운·고대비 테마를 따르며, 기록을 펼친 상태는 창을 다시 열어도 유지합니다. **새 기록**으로 수동 캡처하고, 저장소 아래에서 새로고침·일시 중지·기록 관리를 사용할 수 있습니다. 각 기록은 저장된 전후 내용을 로컬 규칙으로 분석해 `로그인 검증 함수 수정`, `scripts.build 설정 수정`처럼 요약합니다. 분석할 수 없는 변경은 `common.py·git.py 수정` 같은 파일명 요약을 사용합니다. 기능 완성이나 작업 의도를 자동으로 추정하지 않습니다.
   기록을 펼치면 브랜치·HEAD와 **변경 비교 / 복원 / 커밋** 버튼, 파일별 Diff를 확인할 수 있습니다. **이름 변경 / 기록 고정 / 기록 삭제**는 상세 아래쪽과 기록의 우클릭 메뉴에 모았습니다. 직접 적은 작업 이름은 커밋 메시지 초안에도 사용하며, 빈 이름은 자동 요약으로 돌아갑니다. 브랜치마다 일정한 색상을 사용하고 고정·커밋 완료는 별도 배지로 표시합니다. 커밋 버튼은 직전 커밋 경계부터 선택 시점까지의 구간에서 포함한 파일을 대상으로 합니다. 정상 동작 검증 상태는 기본적으로 **미검증**입니다. 삭제 시에는 작업명·시각·브랜치를 확인하며, 최신 기록·고정 기록·활성 초기 상태·최신 커밋 경계·복구용 보호 기록은 삭제할 수 없습니다.
4. **Restore Snapshot**은 현재 파일을 보호 백업한 뒤 생성·수정·삭제 목록을 보여줍니다. 외부 에이전트와 파일 수정 프로세스를 중지하고 최종 승인해야 적용합니다.
5. **Undo Last Restore**는 같은 검토·백업 절차로 이전 복원을 되돌립니다. 이후 추가 수정도 새 비교 화면에 표시됩니다.
6. **이 시점까지의 작업 커밋**은 선택한 스냅샷까지의 구간에서 포함한 파일만 한 커밋으로 만듭니다. 펼친 파일 목록은 기본적으로 전체 포함이며, **−로 제외 / +로 포함**할 수 있습니다. 선택은 새로고침·재시작 후에도 유지합니다. 이전 기록에서 이어진 미커밋 파일도 목록에 표시합니다. 포함·제외 목록 → 준비 승인 → 선택한 파일의 실제 Git 변환 결과 Diff → 최종 승인 순서로 검토합니다. 예를 들어 문서를 제외해 코드만 커밋한 다음, **같은 기록에서 남은 문서만 별도 커밋**할 수 있습니다. 부분 커밋은 **일부 커밋**으로 표시하고 이전 기록 정리를 제안하지 않습니다. 최신 작업 파일은 유지하고 현재 브랜치의 HEAD와 인덱스는 정상 커밋 결과로 갱신합니다. 해당 시점의 커밋 대상 파일을 모두 완료하면 **같은 브랜치의 이전 기록만** 삭제 목록으로 보여주고 별도 승인을 받습니다. 다른 브랜치의 기록은 포함하지 않습니다. 취소하면 기록을 유지하며, 최신 커밋 경계·이후 기록·고정 기록·활성 epoch 초기 상태·보호 백업은 보호합니다.
7. **Review and Push**는 원격·브랜치·정확한 OID를 별도로 검토·승인합니다. 강제 Push, 자동 fetch/rebase, 태그 일괄 Push를 하지 않습니다.

브랜치 또는 HEAD가 바뀐 첫 기록은 **저장 당시 HEAD**와 비교하고, 같은 작업 구간의 후속 기록은 직전 기록과 비교합니다. 새 첫 기록에는 비교에 필요한 HEAD 원본도 함께 보존합니다. 기존 기록은 저장된 HEAD를 Git에서 읽어 비교하므로 해당 Git 객체와 Git 실행이 필요하며, 기존 manifest는 수정하지 않습니다.

기존 Staging·부분 Staging·intent-to-add, detached HEAD, 다른 브랜치 기록은 커밋을 제한합니다. 이미 커밋한 경계보다 이전 기록은 선택할 수 없습니다. 일부 커밋한 같은 경계의 남은 파일은 다시 선택할 수 있습니다. 외부 커밋으로 HEAD가 바뀌면 그 뒤의 새 스냅샷을 기준으로 시작해야 합니다. 사용자가 선택한 경계마다 커밋을 만들며 파일 일부 hunk 선택이나 자동 의미 분석에 의한 분할은 제공하지 않습니다. Git 필터·줄바꿈 변환으로 커밋 바이트는 스냅샷 원본 바이트와 달라질 수 있습니다. 제외 파일·Submodule은 해당 구간에 포함하지 않습니다.

커밋 준비와 Git 훅은 저장소 밖의 별도 작업 폴더에서 실행합니다. 무시된 의존성·로컬 환경 파일은 그 폴더에 없으므로 훅이 실패할 수 있습니다. 훅이 검토한 트리를 바꾸면 생성된 커밋을 자동 reset/amend하지 않고 복구 검토를 요구합니다. 강제 종료 시 Git `index.lock`이 남을 수 있습니다. 확장은 다른 Git 프로세스의 잠금을 자동 삭제하지 않습니다. 실행 중인 Git 프로세스가 없는지 확인한 뒤 잠금과 현재 HEAD·인덱스를 직접 검토해야 하며, 작업 파일과 보호 백업은 유지됩니다.

## 기록 범위와 제외 정책

- 저장소 루트 기준으로 추적 파일과 Git에서 무시하지 않는 미추적 일반 파일을 기록합니다.
- `.gitignore`, Git 전역 ignore, `.git/info/exclude`는 Git 자체로 판정합니다. 이미 추적된 파일은 Git ignore만으로 제외되지 않습니다.
- `.env`, `.env.*`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `id_rsa`, `id_ed25519`, `.npmrc`, `.pypirc`는 추적 여부와 관계없이 기본 제외합니다.
- `allowSensitiveFiles`는 사용자 설정만 허용합니다. 예제 파일도 이름 규칙에 걸리면 명시적으로 허용해야 합니다. 프로젝트 설정은 기본 차단을 해제할 수 없습니다.
- 추가 `exclude`는 Python `fnmatch` 규칙을 사용합니다. `/` 없는 패턴은 파일명, `/` 있는 패턴은 전체 상대 경로에 적용합니다. 경로 패턴의 `*`는 `/`도 포함합니다. 숨김 파일에도 적용됩니다.
- 단일 파일 기본 상한은 10 MiB입니다. 바이너리는 상한 내에서 원본 바이트를 저장합니다.
- 링크·junction·특수 파일·중첩 저장소·Submodule·Python 가상환경 내부를 따라가지 않습니다. sparse checkout과 partial clone은 지원하지 않습니다.
- LFS의 디스크 실파일만 크기 정책에 따라 기록합니다. LFS 원격 서버는 백업하지 않습니다.

알 수 없는 위치에 포함된 모든 비밀을 탐지할 수는 없습니다. 제외 정책 변경은 이후 기록부터 적용되며 과거 기록을 삭제하지 않습니다. **Manage History**에서 검토 후 기록을 삭제할 수 있습니다. 보호 중인 기록은 삭제할 수 없습니다.

## 저장과 안전성

작업 저장소 밖 VS Code `globalStorageUri/repositories/<worktree-id>`에 gzip 압축한 SHA-256 객체와 독립 JSON manifest를 저장합니다. 기록 때문에 현재 브랜치 Ref·인덱스·작업 파일을 변경하지 않습니다. Worktree는 Git common directory가 같아도 별도 ID로 관리합니다.

기본 보존 한도는 저장소별 30일, 일반 스냅샷 1,000개, 실제 용량 2 GiB입니다. 고정 기록, 활성 epoch의 초기 상태, 최신 기록, 미완료 작업의 백업을 보호합니다. 복원·커밋 준비 백업은 최소 7일 보호합니다. 보호 기록이 한도를 초과하면 정리를 요구하며 실패를 숨기지 않습니다. OS 파일 잠금으로 같은 저장소는 한 프로세스만 기록합니다. 다른 창에서는 과거 기록을 조회할 수 있습니다.

파일시스템 이벤트 누락을 보완하기 위해 2분마다 파일 목록·메타데이터, 10분마다 전체 콘텐츠 해시를 재검사합니다. 같은 epoch에서 내용이 같으면 스냅샷을 만들지 않습니다. HEAD/브랜치 변경 시 새 epoch를 생성합니다. 60초는 캡처 **시도** 간격이며, 변경이 계속되면 기록 성공이 지연될 수 있습니다.

다음 한계를 이해하고 사용하세요.

- 미저장 에디터 버퍼를 기록하거나 자동 저장하지 않습니다.
- 여러 파일을 같은 순간에 캡처하거나 원자적으로 복원한다고 보장하지 않습니다.
- 외부 프로세스의 쓰기를 강제 차단할 수 없습니다. 복원 시 외부 수정을 중지해야 하며, 감지된 충돌 파일은 자동으로 덮어쓰지 않습니다.
- 복원에는 작업 파일이 있는 파일시스템의 하드 링크 지원이 필요합니다. 지원하지 않으면 원본을 교체하기 전에 중단합니다.
- 복원은 현재 HEAD·브랜치·인덱스를 유지합니다. 다른 브랜치·Worktree 복원은 제한합니다. 같은 브랜치에서 HEAD가 진행된 경우 파일 Diff를 검토하고 복원할 수 있습니다. Windows/macOS에서 대소문자만 다른 경로가 겹치는 복원은 파일 유실을 방지하기 위해 차단합니다.
- 제외 파일과 한 번도 관리하지 않은 새 파일은 보존합니다. 관리 파일 삭제는 승인 목록과 보호 백업에 포함됩니다.
- 파일 바이트와 실행 권한을 복원합니다. ACL·소유권·타임스탬프·하드링크 관계는 복원하지 않습니다. 새로 교체한 파일은 소유자 접근 권한으로 생성합니다.
- 파일 내용과 manifest의 해시를 확인합니다. 손상·알 수 없는 스키마가 있으면 복원·정리를 중단합니다.
- Git 훅과 서명 설정을 유지합니다. 임의의 훅이 검토 후 파일·인덱스·커밋을 바꾸는 것을 완전히 막을 수 없습니다. 예상과 다른 결과를 알리며 자동 reset·amend하지 않습니다.
- 백그라운드 기록·조회는 네트워크를 사용하지 않습니다. 승인한 커밋의 Git 필터·훅·서명 도구에는 해당 도구 고유의 부작용이 있을 수 있습니다.
- 로컬 기록은 하드웨어 장애·VS Code 사용자 데이터 삭제에 대비한 외부 백업이 아닙니다.

## 중단·실패 후 복구

복원 및 커밋 준비는 `operations/*.json`에 진행 상황을 남깁니다. 강제 종료 후에는 복구 상태를 검토할 때까지 자동 기록과 새 변경 작업을 제한합니다. 타임라인의 **복구 검토**에서 다음을 할 수 있습니다.

- 전후 해시와 현재 Git 상태가 안전한 경우 이전 파일/인덱스로 복구
- 충돌을 보존하고 보호 백업을 저장소 밖의 새 폴더로 내보내기
- 직접 파일·Git 상태를 해결한 뒤 명시적으로 해결 처리

복원 중간에 실패하면 확장이 쓴 내용과 여전히 일치하는 파일만 되돌립니다. 외부 수정이 있거나 Git 컨텍스트가 달라지면 강제로 복구하지 않습니다. 커밋 실패/취소 시에도 준비된 인덱스가 그대로인 경우에만 원본 인덱스를 복구합니다.

복원은 교체 직전 실제 파일을 같은 부모 폴더의 `.dev-snapshot-<ID>.restore`에 먼저 보존합니다. 교체 사이에 같은 경로에 파일이 생기면 덮어쓰지 않고 중단합니다. 중간 종료로 경로가 비었을 때는 복구 검토에서 보존 파일을 다시 연결할 수 있습니다. 정상 완료 후 임시 폴더는 정리하고, 충돌이 있으면 Git에서 무시되는 보존 폴더를 남깁니다. 복구 화면에서 위치를 확인할 수 있으며 백업 내보내기는 원본·교체본·현재 파일과 경로 정보를 함께 저장합니다. 직접 해결 처리 후에도 보존 폴더를 자동 삭제하지 않으므로 내보낸 내용을 확인한 뒤 수동으로 정리하세요. 이 폴더의 용량은 스냅샷 저장소 한도에 포함하지 않습니다.

Python 연결이 끊기면 변경 명령을 자동 재전송하지 않습니다. 창을 다시 로드하고 기록·Git 상태·복구 journal을 검토하세요.

## 코드 구조

```text
backend/dev_snapshot/
  common.py       모델 검증, 경로 안전성, durable write
  git.py          Git CLI 어댑터
  store.py        객체/manifest, OS 잠금, 보존 및 GC
  snapshots.py    제외 정책, 캡처, 중복 제거, 요약
  restore.py      복원 계획, 보호 백업, 적용, 취소, 복구
  restore_io.py   실제 교체 파일 보존, 충돌 방지 게시, 보존 파일 내보내기
  commits.py      검토한 파일의 커밋, 인덱스 복구, Push
  boundary.py     스냅샷 구간 커밋, 격리 준비, 경계와 인덱스 관리
  engine.py       응용 서비스와 자동 기록 스케줄러
  rpc.py          표준 입출력 JSON-RPC 2.0
src/
  bridge.ts       Python 프로세스 및 통신
  extension.ts    VS Code API 연결, Tree View, 승인 흐름
  documents.ts    읽기 전용 검토 및 Diff 문서
  protocol.ts     wire 타입 (도메인 로직 없음)
```

프로토콜 버전은 `hello.protocol = 1`입니다. 요청 ID와 작업 ID를 구분하며, 변경 작업은 `approved: true`, 복원·복구는 추가로 `writersStopped: true`를 요구합니다. 실제 UI 승인은 TypeScript에서 받고 실행 직전의 파일·Git·미저장 상태 검사는 Python에서 수행합니다. RPC는 개인 stdio 파이프에만 연결되고 외부에서 수신하는 포트를 열지 않습니다.

## 검증과 후속 범위

### 로컬 규칙 기반 작업 이름

각 스냅샷의 저장된 전후 내용을 비교해 작업 이름을 자동 생성합니다. Python 함수·클래스, JS/TS의 이름 있는 함수·클래스 메서드·블록 화살표 함수, JSON 설정 키, CSS/SCSS 선택자를 분석합니다. 예를 들어 `validate_login` 본문 변경은 `로그인 검증 함수 수정`, 빌드 명령 변경은 `scripts.build 설정 수정`으로 표시합니다. 알려진 식별자 단어를 조합하는 규칙이며 작업 의도나 기능 완성·테스트 성공을 판정하지 않습니다. JS/TS 분석은 가벼운 선언 탐색이며 모든 문법을 지원하지 않습니다.

제목 생성에는 API·모델·에이전트 호출·Hook·승인·연결 검토가 필요하지 않습니다. 최대 12개 파일, 파일의 각 버전 64KiB, 합계 512KiB를 분석하며 큰 파일·바이너리·지원하지 않는 코드·분석할 수 없는 변경은 기존 파일명 요약을 사용합니다. 기존 기록은 원본 manifest를 바꾸지 않고 표시할 때 갱신하고, 직접 편집한 제목을 우선합니다. 기존 Codex 보고와 관리 UI는 `devSnapshot.showAgentReports`를 켜면 별도로 볼 수 있지만 제목에는 사용하지 않습니다. 과거 연동 설계는 [Codex 연동 기록](docs/codex-history.md)에 보관합니다.

Python `unittest`는 실제 임시 Git 저장소에서 바이트 복원, 기존 인덱스, 민감 파일, 객체 손상, 프로세스 강제 종료, 외부 수정, Git 훅 및 Worktree를 검증합니다. Node 테스트는 Python과의 실제 통신·재시작·오류 처리를 검사합니다. VS Code 테스트는 활성화·명령 등록·디스크 기록·미저장 편집 분리를 검사합니다. UI의 모든 승인 대화상자를 자동 조작하는 테스트는 포함하지 않습니다.

CI에는 3개 OS, VS Code 1.95/최신 안정 버전, Python 3.12와 별도 Git 2.43 코어 테스트를 구성했습니다. 로컬 테스트 통과와 CI 실행 완료는 구분해야 합니다.

`npm run benchmark`는 10,000개·약 100 MiB의 고유 바이너리 파일에서 초기/10개 파일 증분 캡처 시간을 측정합니다. Python 프로세스 peak memory도 출력하며 VS Code/Node 메모리는 포함하지 않습니다. 목표는 초기 10초, 증분 2초이며 하드웨어와 파일시스템에 따라 달라집니다.

2026-10-15 Windows에서 다른 테스트 없이 기본 벤치마크를 순차 재실행한 결과, 초기 캡처 **152.05 → 128.02초**, 10개 파일 증분 캡처 **1.65 → 1.57초**, Python 최대 메모리 **74.69 → 68.13 MiB**를 확인했습니다. 별도 상세 프로파일 실행의 전체 해시 재검사는 **44.02 → 15.01초**였습니다. 작은 파일에도 큰 읽기 버퍼를 요청하던 비용과 변경 경로 비교 비용을 줄였으며, 객체별 durable write와 실제 읽기·해시 검증을 유지합니다. 초기 10초 목표는 여전히 충족하지 못했습니다. 측정 조건·한계·CPU/I/O·검증 결과는 [성능 최적화 보고서](docs/performance-2026-10-15.md)에 기록했습니다.

`npm run benchmark -- --extended --profile --output benchmark-results.json`으로 메타데이터/전체 해시 재검사, 100개 파일 변경, 증분 캡처 5회, 5초 유휴 상태까지 측정할 수 있습니다. 프로파일 시간은 두 작업 스레드의 중첩된 호출 시간을 합산하므로 서로 더하거나 wall-clock 시간과 동일하게 해석하면 안 됩니다. CPU와 I/O는 Python 프로세스만 포함하며, Windows I/O 카운터는 캐시된 전송을 포함하므로 물리 디스크 사용량과 다릅니다.

이후에는 원격 호스트 지원, 격리된 테스트 결과 연결, 미저장 버퍼 보존, 과거 상태의 별도 브랜치 커밋, 검증된 다중 커밋 재구성, 선택적 AI 요약, 동의 기반 원격 백업 순으로 확장합니다.
