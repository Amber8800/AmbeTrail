# AmberTrail v0.2.1 성능 최적화 — 2026-10-15

## A. 확인한 병목과 측정 조건

[snapshots.py](../backend/dev_snapshot/snapshots.py)의 `SnapshotService.read_entry()`는
10KiB 파일에도 기본 한도인 10MiB+1을,
[store.py](../backend/dev_snapshot/store.py)의 `Store.get()`은 100MiB+1을
`BufferedReader.read()`에 요청했다.
버퍼 할당 비용이 실제 콘텐츠 크기에 비해 컸다. 디스크를 제외한 실험에서도
동일한 10KiB gzip 객체를 500회 읽을 때 100MiB+1 요청은 0.897/0.883초,
10KiB+1 요청은 0.022/0.026초였다.

`SnapshotService.capture()`의 증분 경로 선정은 각 파일을 모든 변경 경로와
비교했다. 10,000개 파일과 1,000개 변경 경로의 비교만 3회 중앙값 2.247초였고,
동등한 조상 경로 탐색은 0.0028초였다. 평평한 파일 경로를 사용한 독립 실험으로,
전체 캡처의 개선율을 의미하지 않는다.

변경 전 초기 캡처 프로파일에서 `Store.get()` 누적 시간은 108.17초,
atomic write는 52.67초, gzip 압축은 2.64초, manifest 저장은 0.20초였다.
두 작업 스레드의 inclusive 시간으로, 호출들이 중첩되므로 합산할 수 없다.
안전 절차를 유지하면서 줄일 수 있는 읽기 할당과 경로 비교를 우선했다.

측정 환경과 제한:

- 동일 Windows 호스트(빌드 26200), Intel64 Family 6 Model 140, Python 3.12.10,
  Git 2.54.0.windows.1, 작업 스레드 2개.
- 각 실행마다 독립 임시 Git 저장소·스토리지를 만들었다. seed 42의 고유 난수
  바이너리 10,000개 × 10,240 bytes, 총 97.65625MiB. 기존 벤치마크와 동일하게
  HEAD가 없는 저장소의 미추적 파일이다. 사용자 작업·스냅샷은 사용하지 않았다.
- 아래 표는 같은 `--extended --profile` 도구의 변경 전/후 실행이다.
  OS 캐시는 강제로 비우지 않았고 cold-cache 측정으로 해석하면 안 된다.
  최초 기존 도구 재실행은 초기 194.651초/증분 1.653초/peak 68.87MiB였다.
  도구와 실행 범위가 달라 아래 메모리와 직접 비교하지 않는다.
- 첫 상세 실행의 초기·재검사는 각각 단회 측정이다. 변경 전 초기 측정 일부에 짧은
  회귀 테스트가 겹쳤으며, 시스템 부하·캐시 변화의 영향이 있다. 이후 다른 테스트가
  모두 끝난 상태에서 원본 코드와 개선 코드를 기본 벤치마크로 순차 재측정했다.
  아래 상세 실행과 추가 확인을 구분하며, 감소율은 해당 관측값의 차이다.
- 5회 증분 측정은 매번 새 콘텐츠를 썼다. 장시간 메모리 안정성을 입증하는 시험은 아니다.
- CPU/I/O는 Python만 포함하며 Git 자식 프로세스와 VS Code Extension Host는 제외한다.
  I/O는 Windows `GetProcessIoCounters`로, 캐시된 전송을 포함한다. 물리 디스크 I/O는 미측정이다.
  peak working set은 데이터 생성·모든 시나리오·마지막 객체 검증까지의 프로세스 최대값이다.

## B. 적용한 변경과 안전성

1. 작업 파일 읽기를 `min(관측한 파일 크기, 설정 한도)+1`로 제한했다.
   읽은 길이와 관측 크기가 다르면 실패한다. 파일 형식, 경로·링크, open 전/후
   descriptor signature, 읽기 후 경로 signature, 설정 용량 검사는 유지했다.
2. 객체 읽기를 검증된 예상 크기+1로 제한했다. 크기를 모르는 호출은 기존 전역 한도를
   사용한다. 추가 1바이트로 초과 데이터와 EOF를 확인하며 gzip CRC/trailer와
   SHA-256·예상 크기 검증을 유지한다. 잘못된 예상 크기는 읽기 전에 거부한다.
3. 증분 캡처에서 파일 경로를 부모 방향으로 탐색하며 변경 경로 집합을 조회한다.
   변경 경로 수와 파일 수의 곱에 비례하던 비교를 파일 경로 깊이에 비례하도록 바꿨다.
   디렉터리 이벤트와 직접 파일 이벤트를 모두 처리하고 유사한 형제 경로는 구분한다.
4. 기존 벤치마크에 단계 프로파일, Python CPU/I/O, 재검사·연속 변경·유휴 시나리오와
   JSON 저장 옵션을 추가했다. 새 런타임 의존성은 없다.

포맷(schema 1), 패키지 버전, 재검사 주기(120/600초), debounce,
동시 처리 수, Git 조회·안정성 재확인, post-write 객체 재읽기 검증,
atomic replace, fsync, 용량·보존 정책, 복원·백업 절차는 변경하지 않았다.
초기 객체 읽기 검증 10,000회, gzip 압축 10,000회, fsync 10,002회는 전후 동일하다.

## E. 남은 비용과 제외한 개선

- 초기 10초 목표는 미달이다. 초기 객체별 durable write와 새 객체 재읽기가 남는다.
  변경 후 atomic write 누적 59.27초, fsync 30.51초, 객체 검증 읽기 90.43초이며
  서로 중첩되고 두 스레드가 겹치므로 wall-clock 지연과 동일하지 않다.
- 메타데이터 재검사 7초대의 경로·링크·파일 상태 확인을 유지했다.
  스캔 결과 공유를 검토하려면 경로 교체와 이벤트 누락 검증을 먼저 설계해야 한다.
- HEAD가 있는 대량 수정 상태의 최초 비교 baseline은 파일별 Git blob 조회가 남는다.
  이번 데이터셋에서 그 비용을 대표적으로 측정하지 않았으므로 수정하지 않았다.
- eager Future 제출, 객체별 잠금 사전, 파일 캐시의 장시간 수명은 추가 메모리 분석 대상이다.
  5회 반복 결과만으로 장시간 누적 문제가 없다고 단정하지 않는다.
- TypeScript의 기존 100/200ms 갱신 병합과 숨김 sidebar의 렌더 생략을 확인했다.
  실제 Extension Host 비용을 계측하지 않아 UI/통신 경로는 수정하지 않았다.
- 검증 생략, 검사 주기 증가, 저장 포맷 변경, 더 많은 작업 스레드, 새 의존성은 도입하지 않았다.

## F. 권장 커밋 단위

실제 commit/push/tag/release와 버전 변경은 하지 않았다.

1. 백엔드 변경과 해당 회귀 테스트:
   `perf(snapshot): bound read allocations and match event ancestors`
2. 벤치마크 확장, README와 이 보고서:
   `perf(benchmark): measure capture phases and background resource usage`
