# Codex 작업 설명 연동 — 검증 중

> 0.2.3부터 기본 작업 이름은 로컬 Diff 규칙으로 생성하며 Codex 답변은 제목에 사용하지 않는다.
> 보고·연결 UI는 기본적으로 숨긴다. 아래 내용은 이전 선택형 연동의 설계·검증 기록이다.

## 지원 범위와 버전

검증용 패키지 버전은 **0.2.2**다. 같은 0.2.1의 기존 설치와 새 빌드를 구분한다.
2026-10-15 개발용 Hook 저장소에 실제 최종 답변 3건이 들어온 것을 확인했다.
확장이 사용하는 저장소 연결과 실제 스냅샷 제목 반영은 아직 별도 검증이 필요하며,
v0.3.0 릴리스 완료로 취급하지 않는다. 아래 기존 검증 보고의 미검증 표기는 당시 상태다.
새 코드는 사용자가 명시적으로 허용한 저장소에만 적용되는 선택 기능이다.

OpenAI 공식 문서의 [Stop Hook](https://learn.chatgpt.com/docs/hooks)은
`last_assistant_message`, `session_id`, `turn_id`, `cwd`를 제공한다.
Hook 신뢰 검토가 필요하며, transcript 파일은 안정적인 인터페이스가 아니다.
따라서 transcript·사용자 Prompt·reasoning·도구 로그는 읽지 않는다.
[App Server](https://learn.chatgpt.com/docs/app-server)의 메시지 이벤트는 제공되지만,
기존 VS Code 연결을 수동 구독하는 방식의 안전성과 접근 권한을 이번 작업에서
입증하지 못했으므로 연결하지 않는다. 별도 Codex 세션도 시작하지 않는다.

확인한 로컬 실행 파일은 `codex-cli 0.162.0-alpha.17.2`다.
버전/help 확인은 메시지 전달 검증과 다르다. 현재 지원 검증은 모의 이벤트,
실제 Python Hook 프로세스, 임시 Git 저장소의 코드 연결 및 타임라인 테스트까지다.
중간 진행 메시지·Delta 결합·원본 발생 순서 복원은 **미지원**이다.

## 설정과 해제

1. 사이드바의 **Codex 연동 설정**에서 현재 저장소의 수집을 허용한다.
2. 표시된 JSON을 지원되는 Codex의 저장소 `.codex/hooks.json`에 수동 병합한다.
   기존 `hooks`/`Stop` 배열은 보존하고 AmberTrail handler를 한 번만 추가한다.
   이 명령은 설정 파일을 자동으로 수정하거나 Codex를 실행하지 않는다.
3. Codex의 `/hooks`에서 해당 정의를 검토하고 신뢰한다. 실행 중인 환경의 설정
   재로딩·Hook 지원 여부는 별도 확인해야 한다. 신뢰 우회 플래그는 사용하지 않는다.
4. 평소 작업의 Stop이 발생하면 마지막 답변의 제한된 발췌가 들어올 수 있다.
   기록을 만들기 위한 추가 요청·모델 호출·Turn을 만들지 않는다.
5. 해제는 **Codex 연동 관리 → 수집 비활성화**다. 이전 command의 grant는 즉시 폐기된다.
   재활성화하면 새 설정 예시를 사용해야 한다. Codex 설정에서는 AmberTrail command가
   들어 있는 handler만 수동 제거하고 다른 Hook은 보존한다.
6. **에이전트 기록 삭제**는 이 저장소의 작업 설명과 연결만 삭제하고 수집을 해제한다.
   스냅샷·Git 객체·소스 파일은 삭제하지 않는다.

별도의 자동 Hook 설치/제거 기능은 제공하지 않는다. Windows command 경로에 셸
메타문자가 포함되면 안전하게 예시 생성을 거부한다. 실제 Codex 설정은 사용자가
직접 확인해야 한다. 이번 개발 검증용 Hook 설치는 사용자가 별도로 승인한 작업이며
제품의 자동 설치 기능이 아니다.

## 처리와 보안

- [codex_hook.py](../backend/codex_hook.py)는 최대 256KiB JSON 입력에서 Stop의
  마지막 assistant 메시지만 선택한다. stdout은 항상 `{}`이고 정상 종료한다.
  저장 실패에도 `decision`, `continue`, `additionalContext`, Prompt를 반환하지 않는다.
- [agent_history.py](../backend/dev_snapshot/agent_history.py)는 제목 100자·설명 700자로
  제한하고 코드 블록과 일부 Markdown 형식을 제거한다. 긴 발췌에는 생략 기호를 붙인다.
  별도 요약 모델이나 문장 의미 추론을 사용하지 않는다.
- 비밀 키·일부 자격 증명 패턴을 입력 전체에서 검사하고 발견하면 메시지를 저장하지 않는다.
  **모든 민감정보 탐지를 보장하지 않는다.** 내부 정보가 포함될 수 있어 동의·길이 제한·
  로컬 저장·기록 삭제가 필요하다. 전체 대화 원문은 저장하지 않는다.
- 메시지 원본 발생 시각은 Hook이 제공하지 않아 null이다. 수집 시각을 발생 시각으로
  바꾸지 않는다. 세션·Turn 식별자를 보존하며 동일 grant/세션/Turn의 재전송은 중복 저장하지
  않는다. 다른 Turn의 같은 문장은 별도 기록이다. 같은 ID의 내용이 바뀌어 재전송되면
  첫 보고를 유지한다. 이를 완전한 스트리밍 복구로 취급하지 않는다.
- 서로 다른 Worktree·중첩 저장소는 각각의 승인이 필요하다. 경로만 비슷한 저장소의
  메시지는 받아들이지 않는다. 임의의 메시지 텍스트에서 실행 명령을 만들지 않는다.
- 스냅샷 저장소와 분리된 `globalStorage/agent-history/<repositoryId>`에 schema 1
  메타데이터를 보관한다. 최대 500개·2MiB이며 30일 경과 기록을 새 수집 시 또는 시간당
  정리한다. 현재 보관 한도는 고정 정책이다. 이 저장량은 스냅샷 용량 정책과 별도다.
- OS 소유의 비차단 잠금과 atomic write를 사용한다. 잠금 경합·잘못된 입력·지원하지 않는
  필드·저장 공간 부족에서는 수집이 누락될 수 있다. 누락을 추측하여 새 내용을 만들지 않는다.
- 수집 오류는 내용 없는 로컬 상태 파일로 알리고, 다음 성공 시 해제한다. 상태 파일마저
  쓸 수 없는 디스크 장애에서는 오류 표시도 보장할 수 없지만 Codex 흐름을 재개하지 않는다.
- Webview는 모든 메시지를 `textContent`로 표시한다. 실행 가능한 HTML·명령으로 해석하지
  않으며, 메시지 항목은 복원·커밋 명령을 실행할 수 없다.

## 스냅샷 연결

Stop만으로는 코드 변경의 작성자나 Turn별 범위를 증명할 수 없다. 따라서 수집된 메시지는
우선 **Unlinked(미연결)**로 표시한다. 시간 근접만으로 연결 후보를 확정하지 않는다.

사용자가 **연결 검토**에서 하나 이상의 스냅샷을 선택하면 실제 변경 경로, 트리 해시,
브랜치·HEAD를 보여 준다. 사용자가 확인한 검토 해시가 현재 상태와 일치할 때만
**Confirmed(사용자 확인 연결)**을 기록한다. 여러 메시지와 여러 스냅샷의 연결을 허용한다.
이 상태는 코드 작성자나 테스트 성공에 대한 자동 검증이 아니다.

**Uncertain** 상태의 표시/저장 모델도 구분하지만 자동으로 추측한 관계를 생성하지 않는다.
증거가 부족하면 미연결 상태를 유지한다. 비교 기준이 삭제됐거나 코드 변경이 없는
스냅샷은 확인 연결을 거부한다. 연결 대상이 삭제되면 해당 스냅샷으로 이동할 수 없다.

확인된 연결 제목은 표시 메타데이터로만 쓰며 사용자 지정 제목이 우선한다.
기존 파일 기반 요약·snapshot manifest·복원·Git 커밋 범위는 변경하지 않는다.
손상된 에이전트 메타데이터는 무시하고 파일 이력을 계속 제공한다.

## 로그인·회원가입 시나리오 — 모의 검증

테스트 입력은 `로그인과 회원가입 기능 구현\n에이전트 보고: 관련 테스트 완료`인
Stop 메시지다. 제목은 `로그인과 회원가입 기능 구현`, 설명은
`에이전트 보고: 관련 테스트 완료`로 추출된다. 이는 테스트 성공을 확인한 결과가 아니라
입력된 에이전트 보고의 발췌다. 진행 메시지·Delta는 수집하지 않는다.

임시 Git 저장소에서 `login.py`, `signup.py` 변경 스냅샷을 만들고, 여러 보고를 여러
스냅샷에 명시적으로 연결하는 테스트가 통과했다. UI 모의 테스트는 미연결 보고 표시,
연결 검토·승인, 텍스트의 안전한 표시를 확인한다. 연결 전에는 별도 작업 설명으로,
확인 후에는 해당 스냅샷의 표시 제목·설명으로 사용할 수 있다. Stop만으로는 각 파일의
작성자, 작업 도중의 발언, 테스트 실행 결과를 증명할 수 없다.
이 시나리오는 실제 Codex가 로그인·회원가입을 구현한 실사용 검증이 아니다.

## 검증 및 남은 조건

- 에이전트 백엔드 집중 테스트 22개 통과: 동의/폐기, 중복/재시작/순서, 크기·보존 한도,
  민감정보 거부, Hook 실패, `{}` 출력, 여러 메시지/스냅샷, 연결 검토 해시,
  메타데이터 손상 시 캡처·Diff·규칙 요약 유지, Git·manifest 불변성.
- 새 UI 테스트 4개 포함 확장 단위 테스트 16개 통과. 미연결 표시·승인 취소·연결 검토·
  명령 허용 목록·사용자 지정 제목 우선순위를 확인했다.
- 기존 Node bridge 테스트 3개 통과. 타입 검사 통과.
- `npm test` 전체 실행 통과: Python 135개 중 133개 통과·Windows 조건 2개 skip,
  Node 19개 통과. 이후 최종 보강한 메타데이터 접근 거부·캐시 후 변조·수집 오류 상태까지
  포함한 집중 테스트 22개도 통과했다. 전체 실행은 초기 16개 신규 테스트와 기존 119개를
  포함하며, 추가 6개는 집중 실행으로 확인했다. 타입 검사·빌드도 통과했다.
- 실제 Codex 자동 전달은 아직 미검증이다. 사용자가 이 저장소의 이후 답변만 허용하여
  `.codex/hooks.json`에 검토용 handler를 추가했다. Codex가 이를 신뢰·로드하고 실제 Stop을
  보낸 증거가 필요하다. 과거 대화와 기존 transcript는 읽지 않았다.
- 검증용 handler는 `.test-tmp/codex-live-check`를 사용하는 별도 테스트 설정이다.
  제품 UI의 수집 해제 대상과 다르다. 중지는 이 저장소 `.codex/hooks.json`에서 해당
  `codex-live-check` command의 handler만 제거하면 된다. 다른 Hook을 제거하지 않는다.
- 기존 VS Code 1.95 통합 테스트의 `latestAt` assertion 실패는 이전 작업에서 원본에서도
  재현됐다. 이 실패를 고치기 위해 스냅샷 동작이나 테스트 조건을 바꾸지 않았다.
- 실제 수 시간 운용, Extension Host CPU/메모리, macOS/Linux Hook 실행은 미검증이다.
- Claude Code는 향후 별도 어댑터 후보이며 이번 구현의 지원 대상이 아니다.

현재 실제 수집 검증이 남아 있어 v0.3.0 릴리스 완료를 주장하지 않는다.

## 자원 사용과 추가 모델 사용 검증

Windows/Python 3.12.10의 격리된 모의 보고 500개에서 저장량은 362,910바이트,
수집 함수 지연은 중앙값 9.72ms·최대 24.34ms였다. Python Hook 프로세스 실행까지
포함한 10회 측정은 중앙값 163.77ms·최대 195.31ms다. 실제 Codex 전달 지연과는 다르다.
캐시 로드의 Python 추적 할당은 약 1.41MiB, 최고 약 2.06MiB이며 프로세스 RSS가 아니다.
약 5초의 유휴 폴링에서 측정된 Python CPU 시간은 0초였다. 짧은 측정과 타이머 해상도의
한계가 있으므로 장시간 무부하·메모리 안정성을 입증한 결과로 해석하지 않는다.

동일한 10,000개 파일·97.66MiB 기본 벤치마크 비교는 아래와 같다.
에이전트 수집을 활성화한 동시 부하나 Extension Host 부하는 포함하지 않는다.
OS 캐시는 비우지 않았고 각 1회 측정이므로 작은 차이는 회귀의 증거로 단정하지 않는다.

최초 저장 10초 목표는 여전히 미달이다. 이번 작업에서 이 문제를 해결했다고 주장하지 않는다.
원시 측정은 `.test-tmp/agent-performance.json`,
`.test-tmp/agent-snapshot-performance.json`에 있으며 로컬 검증 자료로만 보관한다.

수집 경로의 네트워크·자식 프로세스 실행을 실패시키는 테스트, 실제 Python Hook의
정상·잘못된 입력·저장 실패 시 `{}` 출력과 정상 종료를 확인했다. 수집기는 Codex/API를
호출하지 않으며 설정 생성에서 쓰는 `subprocess.list2cmdline`도 문자열 생성만 수행한다.
후속 Turn·기록 전용 Prompt·Agent/Subagent를 만들지 않았다. 다만 실제 Codex가 Hook을
호출하는 종단 경로는 미검증이므로 그 환경의 자동 재개 여부까지 검증 완료라고 주장하지 않는다.
